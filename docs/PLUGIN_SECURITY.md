# 外部插件安全策略

## 当前行为

应用不再扫描、编译或加载程序目录下 `parsers/`、`pushers/` 中的 `.java`、`.class` 和 `*.ini` 文件。内置于当前构建产物中的解析器、下载器和推送器仍按原有注解机制加载，不影响正常的视频、音频、字幕和弹幕下载流程。

旧 `Plugin` 与 `CustomClassLoader` 类只作为二进制兼容占位：查询是否需要编译会返回 `false`，任何编译或外部字节码加载请求都会显式失败。当前没有配置、环境变量或命令行参数可以绕过该策略。

如果本地已有自定义插件，请保留自己的源码备份，但不要把它放在应用可写目录并期待维护版执行。维护版不会删除这些文件，也不会读取其内容。

## 为什么不能只加一个确认框

外部 Java 插件与主程序运行在同一 JVM 时，默认拥有与应用相同的文件、网络、进程和凭据访问权限。确认一次来源或限制类名不能阻止插件读取 Cookie、修改下载文件、启动子进程或上传数据；Java Security Manager 也不再是 JDK 21 可依赖的隔离方案。

因此，在可信插件架构完成前，“默认关闭但允许手工开关”仍然不是足够的安全边界。

## 后续插件架构要求

如确实需要恢复第三方扩展，应重新设计为独立插件协议，而不是恢复旧类加载器：

1. 插件在独立、低权限进程中运行，通过版本化 IPC 协议与主程序通信。
2. 主程序只传递完成解析所需的最小数据，不向插件暴露 Cookie、Token、任意文件路径或 Java 对象。
3. 插件包包含固定 ID、版本、兼容 API、入口、权限声明、文件清单和 SHA-256。
4. 默认只允许本仓库签名的插件；第三方签名必须由用户逐个信任，并显示网络、文件和进程权限。
5. 插件安装采用暂存、摘要和签名校验，失败时删除暂存内容；升级与卸载不能触碰下载目录和用户配置。
6. Windows 与 macOS 分别限制插件进程权限，并对超时、崩溃、输出大小和并发数设置边界。
7. 插件禁用或失败时，内置解析器继续可用，错误信息明确指出插件 ID 和恢复方式。

## 恢复前验收门槛

- 威胁模型和 IPC 协议经过独立 Review。
- 未授权插件无法读取 Cookie、fingerprint、下载目录外文件或启动任意进程。
- 篡改的 manifest、摘要、签名和插件内容均被拒绝。
- Windows 与 macOS 上完成安装、禁用、升级、崩溃恢复和卸载测试。
- CI 覆盖恶意插件、超时、超大响应、路径逃逸和协议版本不兼容。

这些条件完成前，`SourcePluginPolicy` 必须保持 fail-closed，`PackageScanLoader` 只能发现随应用构建的可信内置类。
